Teams notifications setup

Return to Project Hub

Notifications stay off until configured. No private data is sent during setup, except when you explicitly use Test notification or enable scheduled delivery.

1. Verify your tenant first

In Teams, open Workflows and look for When a Teams webhook request is received. Confirm your administrator permits that trigger, the chosen connection and an anonymous (“Anyone”) signed webhook. Also confirm your posting action supports your own personal chat. Template visibility alone does not verify permissions or licensing. This integration does not use When an HTTP request is received, a custom connector, an Entra app or premium HTTP actions.

If the tenant requires tenant-user authentication or blocks the trigger/personal-chat destination, leave notifications disabled and ask your administrator. Project Hub does not impersonate a Microsoft 365 user or obtain OAuth tokens.

2. Create a minimal Workflow

  1. Create the Teams webhook workflow, using the trigger above. Choose Anyone only if tenant policy permits. Treat the signed URL as a password.
  2. Add the Teams action Post card in a chat or channel (the exact label can vary). Choose Flow bot, Chat with Flow bot, and your own account as recipient. Do not choose a group/channel unless you intend to share task titles with it.
  3. Set the Adaptive Card input to this expression:
    triggerBody()?['attachments']?[0]?['content']
    Project Hub supplies one Adaptive Card attachment, so no Apply to each, variables, Parse JSON or extra Compose actions are needed. If you use a template, remove any additional/duplicate posting actions.
  4. Save, copy the generated signed Workflow URL, and check the flow connection is healthy. The app accepts Microsoft *.logic.azure.com or *.environment.api.powerplatform.com workflow URLs with a sig parameter. Never paste it into GitHub, a task or chat.

3. Configure Project Hub

  1. Open Settings → Teams notifications & scheduled jobs.
  2. Paste the URL, confirm the tenant/destination checks and save. The server encrypts it using the existing stable BETTER_AUTH_SECRET; it never returns the URL or ciphertext. If that secret is rotated, enter the webhook again.
  3. Use Test notification and confirm both the Workflow run and your personal Teams chat. A successful HTTP response means the webhook accepted the request, not that its later Teams action succeeded.
  4. Enable notifications. Start with Daily digest and Titles and links only. Set the time in Australia/Adelaide. Weekly overview runs Mondays; individual reminders require both the global setting and an explicit High/Critical task reminder date.

4. Enable scheduling without a new Render service

The repository includes .github/workflows/scheduled-jobs.yml. It polls the app about every 15 minutes; all recurrence, deduplication and delivery state lives in PostgreSQL. The app does not rely on an open browser or in-memory timers.

  1. Generate one random secret with at least 32 characters, for example locally: 
    node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
  2. In the existing Render web service, add HUB_JOB_SECRET with that value, then deploy.
  3. In GitHub repository Settings → Secrets and variables → Actions, add repository secret PROJECT_HUB_JOB_SECRET with the same value. Add repository variable PROJECT_HUB_URL with the app's existing HTTPS URL (no trailing path).
  4. Open Actions → Project Hub scheduled jobs → Run workflow. Confirm success and check the last-server-job timestamp in Project Hub settings. Then confirm an actual daily digest. The workflow safely skips when configuration is absent.

GitHub scheduled workflows are best-effort: they may be delayed or dropped, and schedules in public repositories can be disabled after 60 days without repository activity. Monitor Actions; re-enable a disabled workflow there. This is suitable for a personal digest, not time-critical alerting. If guaranteed timing becomes necessary, a dedicated external scheduler/Render cron service would need separate approval. No new paid service has been provisioned. Recurrence also catches up safely when the authenticated workspace is opened.

Reliability and privacy

  • Each notification has a persisted unique ID. Daily/weekly keys prevent duplicate creation; individual reminders are once per task/reminder date. Test messages have a one-minute cooldown.
  • Jobs claim rows transactionally before sending. HTTP 429 rejections retry at most three times, about 15 minutes apart. Authentication/expired URLs and malformed payloads stop with a safe error code.
  • Timeouts, interrupted workers and ambiguous server errors are marked unconfirmed and are not automatically resent. Exactly-once delivery cannot be guaranteed across two independent services. Check Workflow run history before deliberately sending a new test. The payload includes notificationId for optional receiver-side deduplication.
  • Messages contain at most eight task titles/links by default. Optional non-private mode adds short Next Actions; notes, descriptions and progress history are never sent. Flexible work dates alone do not trigger reminders.
  • Logs expose timestamps, type, attempts and safe status codes, never webhook URLs or task payloads. Terminal payloads are cleared. Disable notifications to cancel pending deliveries; an already in-flight request cannot be recalled.

Troubleshooting

Authentication or expired URL: confirm Anyone is allowed, refresh the Workflow URL and replace it in Settings. Accepted but no chat message: inspect the Workflow's Teams connection, recipient and card field. No daily digest: check enabled switches, Adelaide time, the scheduler secret, Actions configuration and last-server-job timestamp. Unconfirmed: check Teams/Workflow history before repeating. Do not share signed URLs in screenshots or logs.
